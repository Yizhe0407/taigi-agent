# 架構

以使用者對 Kiosk 說「201 幾分鐘到？」為例，處理流程如下。

![語音對話流程：音訊輸入 → VAD → ASR → AgentSession → 公車工具與 LLM → 台語轉寫 → TTS → 輸出](images/voice-flow.png)

| 步驟 | 元件 | 資料 |
|---|---|---|
| 1. 偵測說話結束 | Silero VAD（語音活動偵測） | 一段音訊。使用者在小芸說話時插話，小芸會停下 |
| 2. 語音轉文字 | Breeze-ASR-26（語音辨識，ASR） | `201 幾分鐘到` |
| 3. 規則判斷 | `IntentRouter`（正規表示式） | 只說路線號、問跨縣市或轉乘、問時刻表這三種情況回固定說法；其他交給 LLM |
| 4. 選擇工具 | Qwen3.5-4B（語言模型，LLM） | 呼叫 `get_arrivals_here(route="201")` |
| 5. 查詢資料 | 工具 → 交通部 TDX | `往高鐵雲林站：約七分鐘後到這站` |
| 6. 產生回答 | Qwen3.5-4B | 「201 往高鐵雲林站，大約七分鐘後到。」 |
| 7. 轉成台語 | HanloFlow + Taibun | 國語句子 → 台語漢字與拼音 |
| 8. 語音合成 | Piper（以台語資料微調） | 台語語音；Live2D 小芸同步對嘴 |

## 回答中數字的來源

到站時間在第 5 步由程式查詢與計算，第 6 步的模型只把結果改寫成句子。語言模型容易產生看似合理但錯誤的時間，所以流程設計成：

- 每一輪第一次呼叫 LLM 時，要求它一定要選工具，不能直接回答。
- 閒聊、道謝、抱怨、聽不清楚也走工具 `respond_directly`：模型只標出類別，句子由系統從預先寫好的說法中挑選。例外是使用者要求「再講一次」，這時由模型重述上一句。
- 拿到工具結果後，模型才以一般文字回答。一輪最多 8 回合工具呼叫，超過時回「查詢逾時，請換個方式再問一次」。

這個設計有兩個缺口：

- 第 6 步的改寫沒有程式比對數字。prompt 要求模型照抄工具給的時間，但模型仍可能抄錯。
- 模型呼叫工具的格式反覆出錯時，系統會取消「必須選工具」的限制再試一次；若模型因此直接回答，該回答會照樣送出。

## 語音辨識錯誤的處理

假設 ASR 把「201」聽成本站沒有的「207」。工具查不到 207，會依讀音相近程度改查最接近的路線（1 和 7 讀音相近，所以是 201），並把 201 的實際狀態和確認句一起交給模型。小芸的回答會是「你是要問 201 嗎？201 大約七分鐘後到。」

## 工具

| 工具 | 用途 |
|---|---|
| `get_arrivals_here` | 某條路線多久到本站 |
| `get_stop_arrival_statuses_here` | 本站所有路線目前的狀態 |
| `get_routes_at_stop_here` | 本站有哪些路線 |
| `get_routes_at_stop` | 其他站牌有哪些路線 |
| `get_route_stops` | 某條路線停靠哪些站 |
| `get_arrivals_to_destination` | 到某地的本站直達路線與到站時間 |
| `check_stop_on_route` | 某條路線是否停靠某站 |
| `respond_directly` | 非公車問題，由系統挑選固定說法 |
| `end_conversation` | 使用者說「多謝」「按呢就好」時道別並結束對話（僅語音模式） |

到站時間只查 Kiosk 所在的站牌。不提供完整時刻表；需要轉乘的路線由地圖路線規劃處理（見 [路線規劃](route-planning.md)）。

## 模組位置

| 資料夾 | 內容 |
|---|---|
| `backend/agent/` | 對話迴圈：訊息、LLM 呼叫、工具派送、IntentRouter。不含公車邏輯 |
| `backend/tools/` | 提供給模型的工具 |
| `backend/services/` | 公車邏輯（離站決策、路線規劃、Kiosk 設定）與 TTS 流程 |
| `backend/providers/` | 外部資料介面：TDX、ASR、路線規劃引擎 OTP、公共自行車 |
| `backend/voice/` | WebRTC 即時語音，可被打斷 |
| `backend/pipeline/` | 國語轉台語的文字處理 |
| `frontend/` | Vue 前端：離站首頁、小芸、地圖、`/admin` 後台 |

常見修改：

- 新增查詢：照 CLAUDE.md「新增工具流程」，依序修改 provider、service、`tools/`，再登記到 `agent/tools.py`。
- 更換站牌：在 `/admin` 設定，不需改程式。
- 更換公車資料來源：在 `providers/` 新增實作，並修改 `services/departures/provider.py` 的組裝；其他層不需要改。
- 修改特定模組：先查 [架構參考](architecture-reference.md)。

## 限制

- TDX 被限流或無法連線時，系統改用最近一次查到的資料，資料最舊可到約 6 分鐘前。快取存的是預計到站時刻，分鐘數會依目前時間倒數，但這段期間的誤點不會反映出來。超過 6 分鐘則回「查詢失敗」。各層快取見 [架構參考](architecture-reference.md#快取)。
- TDX 只提供「尚未發車」的狀態，不提供預計發車時刻，所以畫面上沒有發車時間。
- 對話紀錄存在單機 SQLite，API 限流與 TDX 限速器只在單一程序內有效；多台機器部署需另外處理。
